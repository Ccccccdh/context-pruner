## 2. 与 v49 的对比（本批唯一改动 = 证据引用化）

| 批次 | 插件臂跨任务均值 | 说明 |
|---|---:|---|
| v49（v42：摘要内嵌源码正文） | **−36.83%**（n=9，正 4/9） | `SELECTED OBSERVED CODE` 占摘要 66%–86% |
| **v52（v51：只列引用）** | **−5.44%**（n=9，正 4/9） | 摘要体积降到 1/6–1/3（离线回放已证） |

**改动方向正确，幅度约 31 个百分点，但离"≥30% 净下降"的验收线还很远**：
本批没有任何一个任务达到稳定正收益，且离散度极大（单样本从 −67.8% 到 +32.1%）。

## 3. 机制观察（本批最重要的发现）

1. **未触发压缩的样本 = 基线**：`atomicity` 三个重复的插件节省是 −0.06% / +0.07% / −1.59%，
   与 v49 的"未触发即持平"完全一致 —— 这是测量口径正确的证据。
2. **触发压缩后仍然是"赢/输交替"**：`lookup` 三次为 +32.1% / −16.8% / +26.0%；
   `referenced` 三次为 +1.4% / −22.3% / −67.8%。压缩**不再必然导致大幅变负**（v49 的 −107%~−140% 消失了），
   但也**没有稳定变正**。
3. **压缩次数从 v49 的"2–4 次"降到 6 个压缩样本共 6 次**（回放预测的"摘要变小后不再迅速重新越阈值"成立）。
4. **`lookup` 任务三臂全部 0/3 通过**：该任务在 v52 里对三个臂都过难（失败原因是宿主特性测试
   `failures=1`，且 3 个样本里 2 个打满 36 次请求上限）。它对本批的节省均值贡献最大，
   却**没有一个臂通过**——这正是"主统计量必须包含失败样本"的原因，也是"节省"不能单独解读的原因。
5. **峰值估算输入**：`none` 38,624 → `pruner_v51` 25,453（−34%），`native_summary` 30,873。

## 4. 不能外推的部分

- 三个固定任务、每任务 3 个重复，**样本标准差不是置信区间**；
- 跨任务均值只是描述性汇总，**不得当作合并效应量**；
- 成功判定是"本机适配的选定测试模块"，不等于完整上游测试通过；
- 供应商返回的输入计数含摘要开销；失败请求可能没有 usage，消耗不可完全观测；
- 费用金额未知（未映射价格），需与厂商账单核对；
- 全部批次运行在 DSH 沙箱内，与 v26–v43 的正常终端批次不可直接比较。

## 5. 下一步建议

1. `referenced_window_wrapping` 的 r3（−67.8%）是本批最大负号样本，且是**未触发上限、正常完成**的样本，
   值得单独回放诊断：压缩后模型多花的输入是从哪里来的（重复读取？恢复失败后重试？）；
2. 阈值提高消融仍按 `V48_V49_DIAG_REVIEW.md` §3.4 单独执行——v52 只改了"引用 vs 正文"一处机制；
3. 插件在本批的 6 次压缩里净收益仍不稳，说明"引用化"是必要条件但不充分：
   需要继续缩小注入体积（例如把 `OBSERVED FILE INDEX` 也改为按需恢复）。

## 6. 审计（独立复核，已完成）

`integrations/openhands/audit_validation_v52.py --out runs/stage5-openhands/django-multitask-v52-pilot-01`
（只读：105 个源文件哈希复核 + 逐样本重跑验收 + 编辑边界 + 归档引用 + 凭据扫描）

| 审计项 | 结果 |
|---|---|
| 样本 | 27/27，`complete=True` |
| 源文件哈希 | 105/105 一致 |
| 最终代码通过（独立重跑验收） | `none` 6/9、`native_summary` 6/9、`pruner_v51` 6/9 —— **与运行报告完全一致** |
| 失败请求 | 三臂均为 0 |
| 压缩事件 | 0 / 4 / 6 —— 与运行报告一致 |
| 编辑边界 | 全部样本通过（改动仅限允许文件） |
| 凭据扫描 | `credential_matches=0` |
| 审计耗时 | `evaluate` **9,014.5 s（占 99.99%）**，`boundary_edit_check` 合计 **2.2 s**，`post_evaluate_verification` 0.03 s |

**两条由审计独立确认的结论：**

1. **性能优化的效果被验证了**：审计的编辑边界检查（3 个可编辑文件）合计只花 **2.2 秒**，
   而全树哈希在 v49 是每样本 15.8 s（冷启 254.6 s）。审计的全部成本现在都在**逐样本重跑验收**
   （约 5.6 分钟/样本：复制约 2 万文件的 Django 树 + 跑选定测试），不再是哈希。
   这也解释了为什么 v49 的审计要 4 小时，以及为什么"多进程并行"在本机不划算（每份副本要重新复制 2 万文件）。

2. **"只统计双方成功"会让插件臂看起来更差，而不是更好**——这是本批最重要的统计结论：

   | 子集 | `pruner_v51` 均值 | `native_summary` 均值 |
   |---|---:|---:|
   | 全部配对（主统计量） | **−5.44%**（wins 4/9） | **−25.28%**（wins 5/9） |
   | API 正常 | −5.44%（n=9） | −25.28%（n=9） |
   | 双方通过且 API 正常 | **−15.05%**（n=6，wins 2/6） | **−55.21%**（n=6，wins 2/6） |

   原因是：正号最大的三对都来自 `lookup_allowed_foreign_primary`，而该任务**三臂全部未通过**，
   于是被"双方成功"子集整体剔除；留下的 6 对恰好是负号样本（`referenced` r1/r2/r3 全是双方成功）。
   **若有人用"只统计成功样本"的口径汇报，插件臂会从 −5.4% 被夸大成 −15.1%。**
   这正是协议里"主统计量必须包含失败样本、成功子集只作敏感性分析"的实证依据。
