## 失败形态

- **7 个触发守卫单元**：autoscale 3 个各拒绝 6/5/5 次，key_rotation 3 个各 1 次，index_rebuild 1 个 1 次。被拒绝输出中 **19 次有 `Final Answer: HANDOFF` 标记、1 次是裸 `HANDOFF`**；它们都无可执行 Action，现行谓词因而确实拦住了这些早停。不能把本确认批描述为“20 次裸 HANDOFF”。
- **3 个工具表不全单元均为 autoscale**：冻结顺序为 `read_policy_definition → read_capacity_guardrails → read_adoption_record → run_guardrail_check`。三行只完成第 1 项有序前缀，随后模型调用 `read_adoption_record` 等错序 Action，并在末尾重复工具。现行守卫在“有 Action”时放行，所以拦早停仍不能保证工具序列。三行各用 **18/17/17 请求**，完整成本 **30,284/30,077/30,422 token**，均严格与语义失败。
- watermark 的 2 个严格失败属于 `contract_placeholder_echo`，即使工具表全齐、守卫零拒绝也会失败。新守卫仅修工具顺序无法消除此类答案合同风险。

## 候选机制与零 API replay 的实际范围

候选宿主守卫可定义为：在四工具表未完成时，若输出无 Action 或 Action 不是**下一项冻结工具**，拒收并重发；完成四项后才允许交接；达到有界拒收次数则将单元计为失败。所有臂装同一守卫，所有尝试与摘要计费。此为**新宿主配置**，不能回填 r17。当前脚本把旧轨迹按该谓词作静态分类：基线和原生摘要 24/24 单元零新增拒绝；插件的 3 条 autoscale 轨迹会被标为错序。它**没有**实际模型续写，也无法证明拒收后模型会改用下一工具。旧 `agent_attempt_records` 有 token，但不是新守卫下的真实续写；因此这一步是故障定位 replay，**尚非安全通过 replay**。

成本压力检查：插件单次已观测最高完整调用为 **3,282 token**。若新守卫每个插件单元再耗 6 次，则额外 **72 请求、236,304 token**；相对当前 334 请求为 **406 > 350**，在该保守压力情形下成本为负。这个数是按**已观测最大调用**构造的压力情形，非模型或供应商的严格 token 上界；正式上限还需计入输出上限、可能的摘要和失败请求。不能只用“同工作量 5/5 正”放行。

## 下一步门槛与停止线

1. 若继续研发，先实现**独立的新 ID** 守卫与诊断审计器，静态错序负控制、裸与带标记交接负控制、重复 Action 负控制、合规基线零拒绝负控制都必须跑通。审计器须在新任务表上端到端运行，并验证源哈希、每次请求与摘要 token、失败/触顶和工具表；不得修旧审计后追认 r17。
2. 获取至少 **3 项新任务** 的真实宿主载荷，用新机制逐边界做零 API 安全 replay：必需事实不丢、冻结工具顺序可保、基线零拒绝、任务各有非零安全候选；把守卫最坏重发、摘要、失败尝试计入**批级完整成本下界**，要求仍为正，且新请求硬顶能覆盖。静态旧轨迹分类不能充当这项门。
3. 只有以上门全部成立，才按用户已有的有界付费授权冻结新任务、机制、守卫、审计器和请求上限，先运行新 ID 小试；成功后再用未参与修改的任务做独立确认。任一任务工具表或严格质量低于基线、审计非空、批级完整成本非正，即停止扩批。

**当前判定：付费门未过。** 旧批严格质量下降、完整成本为负且旧审计有 38 错误；新守卫尚未证明错序后的真实续写，三项新任务的安全空间也不存在可检验数据。本线停在零 API 研发，不进行付费实验。

## v18 零 API 原型补充

新文件 `experiments/runners/crewai_loop_guard_v18.py` 已实现 Action 执行前的**下一项工具名**核对、无 Action/错序/重复 Action 拒收、拒收次数上限及耗尽时抛异常；提供 live、replay 与 native-summary 三种包装器。`tests/test_crewai_loop_guard_v18.py` 的 **8/8 控制通过**：全臂合规轨迹零拒收，裸/带标记交接、错序、重复、多 Action、坏历史、耗尽均拒收；replay 的三次响应计作三次尝试。独立的 `experiments/audits/audit_crewai_handoff_v18_sanity.py` 用 `R18_DEVELOPMENT_TASK_REGISTRY_20261006.json` 的三项**仅供合成控制**任务做正负审计烟测，能拒绝工具表、守卫与完整 token 账本缺陷。该注册表不是新付费任务或独立确认集。

接线检查还发现旧 r17 runner 的 `native_summary` 分支直接返回 `base.NativeSummaryCrewAILLM`，没有实际套用已声明开启的守卫；旧结果里的“全臂守卫”因此不能单靠 `guard_enabled` 字段证明。这是**旧批执行配置的事后发现**，不修改其冻结、审计或结果。v18 提供单独的 `GuardedNativeSummaryCrewAILLM`。

`experiments/runners/run_crewai_handoff_v18_zero_api.py` 使用旧 case flow 的**进程内临时接线**跑了一项确认任务的三臂 mock 烟测：三臂均声明守卫开启；基线/摘要臂各 7 次模型尝试、0 拒收；插件臂注入“第二工具前错序 Action”及“第三工具前交接”，共 9 次尝试、2 拒收，最终工具表全齐且严格成功。输出为 `R18_HOST_PATH_ZERO_API_SMOKE_20261006.json`。独立 `audit_crewai_handoff_v18_sanity.audit_mock_host_smoke` 复核 **23 次 mock 模型尝试、0 次真实 API 请求、错误 0**，结果在 `R18_HOST_PATH_ZERO_API_INDEPENDENT_AUDIT_20261006.json`。mock provider 本来不扣付费请求预算，故不能把 `api_request_attempts=0` 解释为零成本；正式付费路径的每次拒收重发必须由真实 provider 的 `request_budget.consume()` 和 `attempt_records` 双账本核对。native-summary 的 live 包装器另经替身 provider 测试：两次模型响应中首个早停被拒，第二个正确 Action 放行；没有网络调用。

**真实 replay 的确切缺口**：旧 `model_input_traces` 每条消息只保留 `content_tail` 和长度，没有完整消息内容；`agent_attempt_records` 有每次 token/状态，但不含对应完整模型输出及宿主解析后的 Action；`guard_rejection_records` 只留被拒输出的前 200 字符，放行的 Action 没有逐尝试输出记录。因此无法把旧 r17 的每个真实响应喂给 v18 并确认拒收后续写、工具顺序或完整额外费用。静态工具轨分类与 mock 注入都不能替代真实载荷安全 replay。下一版采集需按尝试记录完整或可验证哈希绑定的模型输入、原始/标准化输出、宿主解析 Action、执行工具、守卫判定、provider 输入/输出 token、摘要尝试与全局请求槽；密钥不得落盘。尚无三项新任务的真实载荷及该捕获链，**停止于零 API，不启动付费**。
