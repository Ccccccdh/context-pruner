# v30 的 37.35% 从哪里来，以及 v36 长上下文候选

本分析只使用保存的 v30 SDK 事件、模型 usage、独立审计与零 API 回放；没有新的模型请求。旧轮结果不覆盖，候选尚未做真实模型验证。

## 37.35% 的准确口径

v30 在两个已见合同上各重复三次。对每一对先计算 `(无压缩输入 - 插件输入) / 无压缩输入`，再对六对取不加权均值，得到 **37.35%**（六对均为正）；描述性配对 bootstrap 95% 区间为 **25.70%–49.68%**。若先汇总输入再相除，得到 **43.71%**，这是另一种加权口径，不得替代预定主指标。插件和无压缩各 5/6 正常完成，原生摘要 6/6；六对中两对质量不匹配。

| v30 配对 | 无压缩/插件输入 | 无压缩/插件 Agent 请求 | 插件压缩 | 输入减少 | 双方正常 |
|---|---:|---:|---:|---:|---:|
| Click r1 | 789,716 / 297,619 | 20 / 17 | 3 | 62.31% | 是 |
| Click r2 | 568,091 / 313,004 | 18 / 19 | 1 | 44.90% | 否，插件停滞 |
| Click r3 | 324,389 / 277,991 | 25 / 16 | 3 | 14.30% | 否，无压缩停滞 |
| packaging r1 | 199,673 / 144,699 | 11 / 9 | 1 | 27.53% | 是 |
| packaging r2 | 161,007 / 98,588 | 9 / 7 | 0 | 38.77% | 是 |
| packaging r3 | 240,413 / 153,253 | 12 / 9 | 1 | 36.25% | 是 |

六对供应商输入差额合计 998,135 token。把每组总输入写成“请求数 × 平均每次输入”，用对称算术拆分，约 319,844 token 来自请求数差，约 678,291 token 来自平均每次输入差；**这只是对不同模型轨迹的算术分解，不是因果归因**。插件总请求 77 次、无压缩 95 次。Click r1 的基线长到单次估计峰值很高，是整体节省的重要来源；packaging r2 完全没有插件压缩，仍有 38.77% 输入差，因此不能把六对 37.35% 全归功于压缩。Click r2 插件与 Click r3 基线的 SDK 重复读取停滞使质量不等。v31 继续采用 v30 的 24k/20k/32k 配置并增加共用导航，后续已见任务六对只得到 8.02%；阈值相同不能保证重现 37%。

## 固定插件轨迹的机制估算

沿 v30 插件实际走过的 **77 次请求和相同工具事件**，分别重建未裁剪视图与候选裁剪视图。在每次完整工具批次后的下一次模型调用边界计算 SDK 视图 token；它排除了三组不同决策路径的影响，但假定未来动作固定，因此**不能推断无压缩模型会照同一路径行动或任务会成功**。v30 的原 24k/20k/32k 回放复现实际 9 次压缩，累计视图 token 估计减少 **27.89%**。按样本分别为 Click r1 41.7%、r2 20.6%、r3 39.8%，packaging r1 7.9%、r2 0%、r3 4.6%。这说明压缩对长 Click 轨迹有直接提示长度作用，而 packaging 的大部分组间输入差受请求路径影响。

| 同一固定轨迹配置 | 接受压缩 | 累计视图估计减少 | 结构安全跳过 | 各次压缩的舍弃代码单元数合计 |
|---|---:|---:|---:|---:|
| v30 原配置 24k / 20k / 32k | 9 | 27.89% | 0 | 493 |
| **v36 候选 20k / 16k / 28k** | **10** | **36.46%** | **0** | **464** |
| v33 激进配置 16k / 13k / 24k | 18 | 46.64% | 0 | 1,262 |

舍弃单元合计只是每次压缩的重复计数，不能直接衡量信息损失。16k 配置在固定轨迹上调用压缩器更多，模型可能重读或走不同纠错路径；v32/v33 的真实结果已表明请求路径和质量可以压倒局部视图节省。20k 配置在这六条旧轨迹上提供了更好的机械折中，故另存为 [`ContextPrunerCondenserV36`](../../context_pruner/adapters/openhands_v36.py)，只改变阈值，继承 v11 的证据选择、安全边界和归档检查。它**不是经真实模型证实的新收益**，也不替换 v11/v33。

v35 的短一些的 packaging 基线轨迹在 20k 下零压缩，而 16k 下可压缩一次，说明 v36 只适合预先声明的长上下文验证，不应全局替换当前配置来宣称改进。下轮需采用未接触的长上下文任务，三组共用 v35 只读工具兼容修复与编辑/预算护栏；插件候选固定 v36 20k 配置，至少与无压缩、SDK 原生摘要比较。先冻结任务来源、原版失败/参考通过门控、质量阈值、样本数和完整配对主指标，再发真实模型请求。必要的模块消融应另设压缩关闭组，以区分共同工具修复与插件作用。
