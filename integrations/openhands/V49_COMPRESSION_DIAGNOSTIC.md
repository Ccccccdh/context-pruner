## 1. 核心发现：净输入由"是否触发压缩"决定，而非任务难度

逐样本（v49，插件臂 vs 同任务同重复的无压缩基线）：

| 样本 | 压缩次数 | 摘要字符 | 插件 tokens | 基线 tokens | 净节省 |
|---|---:|---:|---:|---:|---:|
| atomicity r1 | **0** | 0 | 49,791 | 49,818 | +0.1% |
| atomicity r2 | **0** | 0 | 49,841 | 51,091 | +2.4% |
| atomicity r3 | **0** | 0 | 49,836 | 49,819 | −0.0% |
| lookup r1 | **4** | 77,351 | 555,259 | 231,468 | **−139.9%** |
| lookup r2 | 2 | 48,340 | 523,019 | 756,746 | +30.9% |
| lookup r3 | **0** | 0 | 249,739 | 180,716 | −38.2% |
| referenced r1 | 2 | 58,466 | 546,707 | 263,468 | **−107.5%** |
| referenced r2 | 1 | 29,331 | 334,449 | 139,160 | **−140.3%** |
| referenced r3 | **0** | 0 | 141,541 | 364,104 | **+61.1%** |

- **未触发压缩的样本与基线持平**（+0.1%/+2.4%/−0.0%），说明插件在"不动作"时是中性开销；
- **触发压缩的样本普遍大幅变负**（−107% ~ −140%）；
- 唯一的例外 lookup r2（+30.9%）中，基线自身异常昂贵（756,746 tokens，且用满 36 次配额），
  属于基线侧异常而非插件改善。

**原生摘要臂呈现同样的模式**（触发压缩的 r3 = −207.1%、r1 = −71.1%；未触发的 r3 变体 = +5.9%）。
因此**不是 v42 插件独有**：**只要该会话的压缩机制被激活，轨迹就显著变长**。

## 2. 为什么会变长：摘要本身太大，且 2/3 以上是被重复嵌入的源码

Pruner 摘要的分节占比（实测）：

| 样本 | 压缩次数 | 总字符 | **SELECTED OBSERVED CODE** | CURRENT TASK STATE | PROTECTED CONTRACT |
|---|---:|---:|---|---|---|
| lookup r1 | 4 | 77,351 | **51,108（66%）** | 24,735（31%） | 600（0%） |
| referenced r1 | 2 | 58,466 | **50,500（86%）** | 7,216（12%） | 296（0%） |
| lookup r2 | 2 | 48,340 | **35,354（73%）** | 12,232（25%） | 300（0%） |
| referenced r2 | 1 | 29,331 | **22,614（77%）** | 6,342（21%） | 148（0%） |

**摘要的 66%–86% 是 `SELECTED OBSERVED CODE`。**

## 3. 保留性检查：它保住了该保的东西，代价是体积

四个必要项**全部保留**（这是 v42 的设计目标，做到了）：

| 项 | Pruner | 原生摘要 |
|---|---|---|
| 任务契约 / 编辑范围（`PROTECTED TASK CONTRACT`） | ✅ 保留 | ❌ 丢失 |
| 当前任务状态（`CURRENT TASK STATE`） | ✅ 保留 | ❌ 丢失 |
| 最近失败断言 | ✅ 保留 | 部分（仅 2 项） |
| 验证状态 | ✅ 保留 | ❌ 丢失 |
| 恢复提示（"Omitted code is NOT deleted. Recover it using scoped_editor view..."） | ✅ 保留 | ❌ 丢失 |

原生摘要只保留 1,424–4,023 字符，**丢掉了任务契约与当前状态**——这解释了它为什么同样表现不佳乃至更差。

**Pruner 的问题不是"丢了必需信息"，而是"为了不丢，把源码又抄了一遍"。**

## 4. 关于"压缩必然有害"的结论限定

必须澄清一个**混淆**：长轨迹**既导致**更多 token，**也触发**压缩（压缩阈值按输入量判定）。
所以"触发压缩的样本更贵"部分是**选择效应**，不能直接读成"压缩造成变长"。

可用于区分的是**摘要体积**这一可独立观测的量：
单次压缩注入 29k–77k 字符（约 7k–19k tokens），而它替代的前缀是被遗忘事件；
当摘要中被嵌入的源码本就可达（同一文件可用 `scoped_editor view` 重新读取）时，
**这部分注入是纯增量的**——它不携带模型无法重新获得的信息。

**建议的机制修复（按优先级）**

1. **`SELECTED OBSERVED CODE` 改为"引用"而非"正文"**：只保留 `路径 + 行号范围 + 内容摘要`，
   让模型按需 `view`。这是本次诊断最直接对应的一处；
2. **给摘要设硬性字符预算**（例如 ≤8k 字符），超出部分按优先级截断并保留恢复指引；
3. **提高触发阈值作为单独消融**（不与其他改动混在一起评估）；
4. 用**同一轨迹回放**验证保留率与峰值，再冻结新版本做付费验证。

## 6. 机制修复与离线回放验证（已完成，零 API）

### 6.1 实现

新增 `context_pruner/adapters/openhands_v51.py`：**v42 的算法不变，只把"被选证据单元的正文"换成"引用"**。

摘要里原本会粘贴每个单元的完整源码（`u['text']`），而这些正文是冗余的——同一份摘要已经带有
`OBSERVED FILE INDEX (path, version, view_range)` 与 `OBSERVED SYMBOL LOCATIONS (name:start-end)`，
且前缀明确指示用 `scoped_editor view` 恢复被省略的代码。v51 保留：

- 相同的 trigger / target / hard 预算与视图裁剪逻辑；
- 相同的受保护最近编辑窗口、证据排序（含"已编辑符号"加权）；
- 相同的受保护契约 + 当前状态注入（继承 v42）；
- 相同的结构校验与"拒绝截断必需上下文"行为；
- 相同的审计字段，另加 `reference_only_chars` / `body_chars_avoided` 便于离线复核。

**这是诊断第 4 节第 1 项，"提高阈值"（第 3 项）刻意分开，便于单独消融。**

### 6.2 回放验证（`integrations/openhands/replay_v51_reference_only.py`）

对 v49 的 9 条插件轨迹逐条回放，同一事件流分别喂给 v42 与 v51：

| 样本 | 适配器 | 压缩次数 | 摘要字符 | 被遗忘事件 | 峰值 tokens | 必需标记 |
|---|---|---:|---:|---:|---:|---|
| referenced_window r1 | v42（内嵌正文） | 2 | **58,084** | 67 | 19,734 | 全保留 |
| referenced_window r1 | **v51（仅引用）** | **1** | **4,637** | 40 | **18,955** | **全保留** |
| lookup r2 | v42 | 2 | 48,512 | 77 | 19,803 | 全保留 |
| lookup r2 | **v51** | **1** | **9,018** | 60 | 19,803 | **全保留** |
| referenced_window r2 | v42 | 1 | 29,014 | 36 | 19,487 | 全保留 |
| referenced_window r2 | **v51** | 1 | **8,194** | 36 | 19,487 | **全保留** |

要点：

1. **保留性无损失**：五项必需标记（任务契约、当前状态、恢复提示、文件索引、符号位置）
   在两种适配器下**全部保留**；
2. **注入体积降到 1/6 ~ 1/3**（58,084 → 4,637；48,512 → 9,018；29,014 → 8,194）；
3. **峰值下降**（19,734 → 18,955）；目标上限为 16,000，v51 已更接近；
4. **压缩次数减少**（2 → 1）：摘要变小后不再迅速重新越过触发阈值，这一点对"压缩越频繁越贵"
   的观测是直接对症的；
5. 未触发压缩的 4 条轨迹（atomicity ×3、lookup r3、referenced r3）两版行为完全一致，
   因为它们本就不进入压缩路径。

**未验证的部分（不得据此宣称收益）**：回放只证明"保留性不变、注入更小、峰值更低"，
**不能证明整任务输入下降或质量提升**。后者必须在冻结新版本后由付费批次验证。

### 6.3 回放中发现的一处事实

保存的事件里，动作判别符是 `verification_tool_v32.ScopedTestsAction`（**不带版本后缀**），
说明当轮实际生效的验证工具类型来自 `verification_tool_v32`，而不是我此前以为的
`verification_tool_django_v49`。回放必须注册正确来源才能解析记录；这一点已写入脚本注释。
