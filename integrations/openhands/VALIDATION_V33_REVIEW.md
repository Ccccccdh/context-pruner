# v33 编辑重试修复与三项目开发复验（2026-09-28）

## v32 低结果的可核查原因

v32 的 python-dotenv 合同要求新函数返回与现有 `dotenv_values` 完全相同的值。多数初版实现先合并重复键再调用插值，导致 `SECOND=${FIRST}` 在后续 `FIRST=final` 覆盖后变成 `final`，而现有函数按读取顺序得到 `1`。v32 三组在该任务的初次宿主验收均只有 0/5 通过；错误在压缩前就已存在。

失败后的纠错轨迹产生了用量放大。v32 插件组的 python-dotenv 第 2、3、4 次各调用 36 次 Agent 请求，其中两个轨迹反复提交 `old_str == new_str`；插件组全部 15 样本的编辑错误 25 次，均为无变化替换。它们的压缩发生在长循环形成之后，6 次压缩虽将对应视图从约 24k 缩到约 14k–16k，却不能撤销此前的请求或保证后续编辑正确。v32 插件的 15 对输入均值因此为 -88.99%，完成 10/15；基线完成 12/15。组间轨迹及失败纠错差异是主要可见因素，不能将整个负值归因于压缩算法。

## 修改与运行

v33 在三组共用的编辑器中加入 [edit_retry_guard_v33.py](edit_retry_guard_v33.py)：相同的 `old_str/new_str` 立即返回短错误，连续两次无变化时先要求查看当前函数，避免旧工具把完整替换文本重复回显。三组的初始与纠错提示均明确要求小范围、有实际变化的编辑。插件候选仍使用 v11 证据选择算法，触发/目标/硬上限从 24k/20k/32k 调为 16k/13k/24k，以便在上下文增长时更早处理。SDK 用户状态移至实验目录。v32 原件没有改动。护栏对三组共用，阈值只作用插件，因此本轮不能分离两个改动的效果。

本地护栏测试 2/2 通过，原版回归通过而新合同失败、参考实现通过的门控复用 v32。最早两个小试目录分别在首个模型请求前因 SDK 锁文件权限、首个网络连接因 `WinError 10013` 失败，均停止并保留，未并入效果统计。新目录 9 样本小试独立审计：无压缩 2/3、原生摘要 3/3、插件 2/3，插件 3 对输入均值 +1.46%；插件未触发压缩，因此只是运行检查。随后冻结相同代码在另一新目录运行 45 样本开发复验；全部样本保留，无供应商失败请求。

## 判断与下一步

v33 是查看 v32 失败后在同三个任务上进行的开发复验，不能与 v32 的 -88.99% 简单相减并宣称 94.31 个百分点的因果改进。短任务中仅 2/15 插件样本压缩，当前三项目集合不适合证明压缩机制带来稳定 30% 收益。后续应先用保存的长轨迹做零 API 检查点回放，确认更早压缩对任务合同、可恢复代码和工具结构的影响；然后冻结有实际上下文压力的外部新任务，并单独消融编辑护栏与压缩阈值，才可作为结项效果证据。本轮不继续在相同任务上付费调参筛选百分比。
