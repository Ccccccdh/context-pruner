# CrewAI r4：交接事实与格式分离的开发门控（草案）

## r3 经验事实与边界

r3 的冻结质量结果保持原样：无压缩 3/9、原生摘要 5/9、插件 3/9。离线重放 27 份原始交接，三臂的“事实齐全”分别为 9/9、9/9、8/9；其中插件 `incident_triage` 第 3 次重复只输出 `HANDOFF`，必须继续算事实缺失。严格字面 `HANDOFF ` 的首轮输出为 3/9、5/9、3/9。其余事实齐全的交接有冒号、全角冒号或无标记等格式差异。这些分类仅用于设计 r4，**不追溯更改 r3 成功数或节省率**。

r3 的该插件失败样本中，调查角色最后一次模型输入仍有 `degraded`、`3.8` 和 `HANDOFF` 指令。因此现有证据只支持“输出没有使用可见事实”，不能证明是插件删掉了事实。r4 需记录压缩前后输入摘要、模型原始输出和补救请求，才能进一步归因。

## r4 预注册质量合同

1. 先保存调查角色的原始首轮输出及其输入、工具调用、token 和压缩记录。独立计算 `facts_present`、`strict_marker`、`first_pass_valid`、`needs_recovery`；首轮质量永不被格式修补或重试覆盖。
2. 若事实齐全、单行，允许零 API 的**纯格式规范化**：删除可识别的 `HANDOFF` 标记变体，生成 `HANDOFF ` 加原有正文。若原输出无标记，则只加标记。该步骤不能补充、改写或推断事实；原输出与规范化结果都须保存。用于第二角色的交接文本应标明来自格式规范化。此过程应对三臂一视同仁。
3. 若事实缺失或多行，不能本地补事实。最多允许一次单独计费的调查角色补救请求，明确重读**已经取得的当前工具返回**并输出含两项事实的单行交接。补救阶段不得再次调用原工具；其模型输入、输出、失败、请求数和 token 全部计入该臂。若补救仍失败，记为失败，不进入第二角色。首次输出仍作为主要质量指标；补救后成功率单列。
4. 第二角色仍需实际接收交接、调用指定工具一次，最终 `RESULT`、工具隔离和角色安全门控保持 r3 语义。主质量比较同时报告首轮事实、首轮严格格式、补救后完整任务成功，不得用格式规范化后的成功率替代首轮质量。
5. 完整 token 包含两角色 Agent、任何补救请求和原生摘要；失败、提前停止、触顶样本仍进入配对分布，并单列质量。报告每任务、每臂成功率与成对质量退化，只有质量不劣时才能解释 token 节省。

## 零 API 与冻结前条件

`experiments/runners/crewai_handoff_quality_v4.py` 是前瞻性判定器；`tests/test_crewai_handoff_quality_v4.py` 对 r3 原始 27 行**只读**重放，覆盖三种标记变体、无标记、缺事实与多行，并保证缺事实不能被本地规范化。它不是 r3 重评分工具。

已实现独立的 `experiments/runners/run_crewai_handoff_v4.py` 和 `experiments/audits/audit_crewai_handoff_v4.py`。补救仅使用从调查角色模型输入中读出的真实 `Observation:` JSON，创建**无工具**调查角色，最多调用一次。原始首轮、补救原文、用于第二角色的交接、额外请求、压缩与摘要用量分别记录；审计独立重新计算质量，不导入 runner/判定器。mock 的 `incident_triage` 第 3 次插件样本人为注入 `HANDOFF` 缺事实输出，以检验补救路径，不是付费结果。

零 API 门控：`crewai-two-role-r4-mock-gate-01` 完成 27/27，审计 `complete: true`、`errors: []`、API 请求 0。首轮事实无压缩 9/9、原生摘要 9/9、插件 8/9；插件唯一缺事实样本触发一次无工具补救并完成任务。补救后的 9/9 **只说明 mock 机制可运行**，不表示真实模型质量达标。`tests.test_crewai_handoff_v4` 与 `tests.test_crewai_handoff_quality_v4` 共 6/6 通过，另有旧 `tests.test_crewai_handoff` 4/4 通过。

预定付费 pilot 为 `incident_triage` 一任务×3 次同输入重复×3 臂，共 9 样本，请求总上限 60。模型 `deepseek-v4-flash`，endpoint `https://api.deepseek.com`；provider soft/target/hard 为 1200/900/3000 token，固定保留 300，Agent 单答最多 512，摘要最多 1024、每角色最多 4 次。具体完整参数及六个源码/任务/协议哈希写入 `PRE_RUN_FREEZE_TWO_ROLE_R4_PILOT.json`。正式审计必须带 `--freeze`，核对这些值、批次名、完整样本网格及请求账本。

本地模拟门控批次 `crewai-two-role-r4-mock-pilot-freeze-gate-01` 使用**同任务/方法/重复/预算**、`--mode mock`、请求上限 60。只在零 API 审计时允许 `--dry-run-mock` 忽略冻结文件的付费批次名及 `mode=api` 与模拟批次的 `mode=mock` 差异，其他字段仍须完全一致；正式付费审计绝不传该标志。这个机制只证明冻结门控本身能工作。

pilot 仍是开发试验；其质量与完整 token 节省须以真实三臂输出、独立审计和首轮事实/补救后成功率共同解释。付费前不需要再扩大样本；正式批使用新目录，不覆盖 r3 或模拟门控。新任务应作为最终确认，现有三个模拟任务仅作机制开发。
