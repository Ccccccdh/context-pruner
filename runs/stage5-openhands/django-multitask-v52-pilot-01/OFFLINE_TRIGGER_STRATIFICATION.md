# v52 补充离线实验：按实际压缩触发分层

日期：2026-10-02。只读 `report.json`、`pruner-state.json` 与 SDK 事件；零 API 请求，未修改任何样本工作区。

## 方法

对同任务、同重复的 `none` 和 `pruner_v51` 读取 provider `prompt_tokens`，计算
`(none - pruner) / none`；压缩次数取插件样本 `pruner-state.json.audit` 的条目数。
首阶段请求数用于解释轨迹长度。此分层是事后诊断，不是随机分配的机制对照。

| 任务 | 三次插件压缩次数 | 三次配对输入节省 | 首阶段请求数 none → pruner | 任务均值 |
|---|---|---|---|---:|
| `referenced_window_wrapping` | 0 / 0 / 0 | +1.40% / −22.32% / −67.79% | 13→13 / 17→19 / 7→14 | −29.57% |
| `list_editable_atomicity` | 0 / 0 / 0 | −0.06% / +0.07% / −1.59% | 6→6 / 6→6 / 6→6 | −0.53% |
| `lookup_allowed_foreign_primary` | 2 / 2 / 2 | +32.11% / −16.77% / +25.96% | 26→23 / 20→26 / 26→26 | +13.77% |

## 发现

1. v52 的 6 次压缩只发生在 `lookup` 三个插件样本。该任务三臂最终代码均未通过，因此其正的输入节省不能表述为在成功完成任务的前提下节省。
2. 最大负号 `referenced` r3 没有压缩：插件臂首阶段 14 次请求，基线 7 次；两臂的工具观测中，逐字节相同的重复载荷均为 0。额外消耗来自不同的导航轨迹，不能归因于压缩后信息恢复，也不能靠完全相同的输出去重来直接消除。
3. v52 跨任务描述性均值 −5.44% 混合了未触发时的轨迹波动与触发时的机制效果，不能单独当作压缩净效应。v53 应同时报告触发次数和按任务配对结果，尤其检查阈值提高后 `lookup` 是否减少触发、质量是否改变。

这些观察不证明插件在 `lookup` 上产生因果收益。三臂各自独立调用模型，轨迹、请求数与终止状态均可变化。
