## 1. 这批做了什么

v4 的压缩资格只问「这段文本是否已逐字送达过」，于是把只出现在 `read_django_aggregation` 源码输出里的字面约束 `existing_annotations` 换成注释，插件严格质量 0/3。v5 把资格判据改成**先查已注册字面约束集**：

1. 命中已注册字面的工具输出**逐字固定**，任何一次调用都不允许被注释替换（Django：`read_django_aggregation` = `ordering`+`existing_annotations`，`read_django_count_call` = `filter`）；
2. **最近一次工具组**（最新一对 `function_call`/`function_call_output`）全文保留；
3. 只有既非约束承载、又非最近工具组、且已逐字送达、且能解析出**注册路径+行范围**的工具输出，才被替换为确定性注释；注释写明 `repo/path`、`lines first-last`、字符数与行数，并提示重发该工具即可取回；
4. 每次调用跑**字面生存守卫**（逐承载工具归属 + 出现次数），任一净损失即整份回退并计数；
5. 过滤后字节数超过硬上限（65,216）或没有严格变小，同样整份回退并计入 `budget_fallbacks`。

任务陈述单元中命中字面的 4 个单元额外注册为 `literal_units`；注册表 `experiments/runners/openai_agents_literal_registry_v5.py` 在任何运行前用公开源码文本**自校验**（路径、行范围、归属字面都必须对得上），审计独立重算注册表指纹。

矩阵与 v1–v4 相同：`django_count_annotations` 1 任务 × 3 重复 × `none`/`pruner_v1`/`native_summary` 3 臂 = 9 样本；`deepseek-v4-flash`、禁隐藏 thinking、provider soft/target/hard 2000/1500/6000、输出上限 1024、全局请求上限 100、三臂轮换、逐样本落盘。仅发送公开问题陈述、固定公开基线源码范围与工具结果；`manifest.json` 的 `data_class` 为诚实的 `public_source_diagnostic`。

零 API 门控 `tests.test_openai_agents_evidence_safe_retention_v5` 在付费前已通过（21 tests：20 通过 + 1 父门控子进程跳过项），冻结的 v1–v4 五个测试模块 25 tests 全通过，v2/v3 审计器在各自冻结批上仍 `complete: true`。

## 3. 约束保留与资格判据证据

九个样本的每次模型边界都有证据文件（`input-evidence/*.jsonl`），只含哈希、长度、布尔与计数。

| 重复 | 插件最终 `model_input` 字面命中 | 与基线的字面出现次数 | 固定输出 | 被注释替换 | 注释带指针 | 最近工具组全文保留 | `task_anchor_restore_failures` |
|---|---|---:|---:|---:|---:|---:|---:|
| 0 | 全 True | 与基线完全一致 | 3 | 1 | 1 | True | 1 |
| 1 | 全 True | 与基线完全一致 | 3 | 1 | 1 | True | 1 |
| 2 | 全 True | 与基线完全一致 | 3 | 1 | 1 | True | 1 |

- **v4 的缺陷已闭合**：`existing_annotations` 在插件臂最终 `model_input` 中命中为 **True**，出现次数（3 次）与基线、原生臂**完全相同**；三次插件样本的 `evidence_registered_literals_present_final` 四项全 True，审计逐字面逐边界核对 `complete: true`。
- 固定原因逐样本一致：`{'registered_literal': 2, 'most_recent_tool_group': 1}` —— 两个约束承载输出被注册表固定，最新一对工具调用全文保留。
- 唯一被省去的输出是 `read_django_count_entry`（不承载任何已注册字面），其注释带 `django-16263/django/db/models/query.py lines 610-632` 指针；三次样本 `elided_outputs == notes_with_source_pointer == 1`，`pointer_coverage: true`。每个样本节省 616 字节。
- 受保护 Responses 工具组在每次过滤前后组 id、输出配对数一致；唯一变化的输出文本就是本模块的注释，且注释保留了 `call_id`。
- `task_anchor_restore_failures` **逐样本、逐模型调用持久化**，总数 3（每个插件样本 1 次），基线/原生臂为 0；`restore_failure_is_whole_prefix_fallback: true`，触发原因为 `protected_tool_group_changed:baseline:...`，该次调用整份回退（证据文件 `filter_before` 与 `filter_after` 的 `input_bytes` 完全相同），没有部分恢复，也没有声称该次压缩成功。

## 4. 成本为负的机制诊断

质量门槛通过了，成本却从 v4 的 +7.21% 变成 −79.79%，方向反转的原因有三条，都可以从证据核对：

1. **插件臂多走一次模型调用。** v4 删掉了三个源码输出（包括 4,896 字符的 `read_django_aggregation`），第二轮载荷很小，模型两轮就给出结论；v5 把两个约束承载输出整体固定，第二轮载荷只省了 616 字节，模型需要第三轮才收口。`model_calls_delta = +1`，这一项的代价大于本批全部压缩收益。
2. **本批还含一个自我造成的假阳性回退。** 每个插件样本第 3 次调用都出现 `protected_tool_group_changed:baseline:...`，但证据显示该次 `filter_before` 与 `filter_after` 的 `input_bytes` 与组哈希完全相同 —— 也就是说**载荷没有变**，被判定为「变了」的是基线本身。根因：`_group_hashes` 在**每一次**调用（包括过滤后的观测）都用 `setdefault` 写基线，而一次过滤后的观测里那份 4,896 字符的输出已被替换成注释；下一次调用未经过滤的 `filter_before` 与这条被污染的基线相比自然「不一致」。这个回退让第 3 次调用完全无法压缩。
   `tests/test_openai_agents_group_baseline_diagnosis_v5.py` 在零 API 下复现了该缺陷（v5 现场版：646 字节、2 次调用中 1 次被回退；仅把基线改为「只从未被改写的观测取基线、并按公共前缀比较」后：1,292 字节、0 次恢复失败、0 次回退），并断言付费批证据文件里 `filter_before` 与 `filter_after` 字节相同。
3. **即使修好假阳性，成本仍为负。** 用同一字节轨迹推算：修好后第 3 次调用从 8,191 降到 7,545 字节，约 232 估算 token，插件输入从 5,213 降到约 4,981 —— 仍远高于基线 2,874，且第 3 次调用本身还在。差值主要来自「意图不同的机制」：v5 的规则**必然**把承载约束的 4,896 字符源码在每一轮重传，v4 的规则**必然**把它删掉。质量与约束保留的代价就是这份重传。
4. 因此**不扩大样本**，也**没有**为了改善成本而再跑一个付费批次：预注册口径下，修好第 2 条缺陷仍达不到正节省，再花请求只会重复同一个结论。第 2 条的修正**没有**回写进 v5 冻结源码（冻结哈希与独立审计必须能复现本批），已在诊断测试中记录为版本化修复项，供下一版（v6）零 API 先行验证后再决定是否值得付费。

## 5. 与既有批次的关系与边界

- 与 v4 相比：v4 保住了问题陈述里的字面，丢掉了工具输出里的字面（插件 0/3、配对 +7.21%）；v5 把两类字面都保住（插件 3/3），代价是成本 −79.79%。**两版都不满足预注册验收线，失败方向相反。**
- 与 v3 相比：v3 全量锚定 → 零节省、−33.79%；v5 是「注册表驱动的最小固定 + 可指针回取的选择性省略」，两者都不是有效节省。
- 本批只有 **1 个任务、3 个重复**，且 Django 任务在 v1–v4 已参与调参，**不是**未参与调参的盲测确认批；禁止外推到多任务、其他宿主或真实软件修复，也禁止与 CrewAI / OpenHands 的百分比合并。
- 证据只有哈希、长度、布尔与计数，不保存原文；独立审计通过只说明冻结哈希、账本、资格判据、质量口径、字面保留与计数一致，**不证明语义等价，也不构成成本有效的结论**。
- 本批 9/9 样本全部报告（无失败尝试、无触顶），未做任何事后改判或样本筛选；「被固定」只保护**已注册**字面，注册表之外的同义表述不在保护范围。

## 6. 下一步

1. 把第 4 节第 2 条的基线缺陷作为 **v6** 的唯一机制变更先做零 API 验证（含本批证据文件回归），确认 `task_anchor_restore_failures` 归零。
2. 若仍要求正节省，需要新的机制方向而不是扩样：例如对承载约束的大块源码做**行范围级**省略（保留约束行逐字 + 对省略的行区间给出行号指针），从 4,896 字符里真正省出空间；该方向必须先在零 API 下证明「逐字面命中与出现次数不低于基线」。
3. 只有在质量不劣、完整总 token 稳定为负（即节省为正）之后，才按交接约定换**未参与调参的新公开仓库任务**做 3×3×3 确认。
