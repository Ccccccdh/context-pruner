丢失发生在**模型调用本身**：模型在该次调用里没有产出合同要求的那一行 HANDOFF，而是产出了一段中文引子。

## 3. 与"合同被压掉"的关系

判决器要求首轮交接行以 `HANDOFF` 开头。决定性调用（第一角色最后一次模型调用）的输入视图里：

- **无损的 21 个样本**：视图里始终存在第一角色的任务陈述消息，它含"最终只输出一行以 HANDOFF 开头的交接内容"这条输出格式合同。对照 `none` 臂，9/9 样本的视图里任务陈述都独立存在（视图 26–30 条消息）。
- **丢失的 6 个插件样本**：压缩视图（8–9 条消息）把任务陈述折叠进合并的历史块，**6/6 都不再含合同**；模型随后产出中文引子而不是 HANDOFF 行。

同一机制分支里，合同在场时首轮 21/21 齐全、合同缺席时 6/6 丢失——这是**记录数据内的完全分离**，不是因果证明，但它与"模型没有收到输出格式要求"这一解释一致，并且是 r9 机制修改的直接依据。

**另一条可核对的线索**：6 个决定性调用的 provider 输出 token 是 232–313，而记录下来的 content 只有 9–32 个字符（其余调用 87 token 对应 283 字符）。也就是说，这六次调用报告的补全 token 远多于记录下来的文本。**本诊断不能确定这些输出去了哪里**：r8 的行里只保存了净化后的文本，`raw_response_characters` 与 `normalized_response_characters` 在全部 27 行里逐行相等，因此无法区分"模型生成了 HANDOFF 行但被净化丢弃"与"模型从未生成 HANDOFF 行"。这一点保留为**未解释的观测**，不做推测。

## 4. 对 r9 机制的直接含义（已在 v9 中实现）

1. **压缩侧要保证的是"呈现"，不是"存在"**：事实在压缩视图里存在并不够，承载**输出格式合同**的那条消息也必须活着。v9 因此把第一角色任务陈述（唯一非 system 且带冻结 `HANDOFF` 标记的消息）在合同中缺席时**逐字钉回**。
2. **工具证据必须逐字钉住**：v9 把冻结工具结果里包含必需字面量的最短证据片段（即 `build_tools` 实际返回的 JSON 字节）逐字附加到压缩视图，使"事实存在"不再依赖任何后置补救。
3. **回退必须确定性且计数**：若钉住后仍有必需字面量缺失，或钉住越过冻结硬预算，v9 改为投递**未压缩全前缀**并计入 `required_fact_whole_prefix_fallbacks` 与原因，而不是静默丢字面量。
4. **补救路径保留并仍计费**：v9 不删除补救调用，否则"首轮变好"可能只是把成本挪到别处。

## 5. 边界

- 本诊断只读一批 27 个合成运维样本；温度 0 仍有独立轨迹差异，跨批差值不是自动因果证据。
- "合同缺席 ⇒ 首轮丢失"是 27 个记录样本内的观察，不是受控实验；r9 的付费批才是对该机制的检验。
- 旧批严格 6/9 与语义 9/9 的结论保持不变，本文件不改写任何 r8 评分。
- 3 任务 × 3 重复无法建立跨任务稳定结论，跨宿主百分比一律不得合并。
