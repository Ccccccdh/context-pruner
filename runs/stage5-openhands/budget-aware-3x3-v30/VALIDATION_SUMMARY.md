## 预算修改实际覆盖

全部 267 次 Agent 请求保存了实时预算提示和工具限制；9 次原生摘要请求计入共享输入。无请求额度或 token 硬限额耗尽，最大 Agent 请求数 27。首轮 Click 无压缩组因单次输入余量进入 Finish-only，真实接口接受指定工具并成功结束。

本轮 **没有触发 Verify-only 或第 35/36 次边界**；该边界由此前模拟供应商响应、真实 SDK 会话测试覆盖。因此真实运行证明提示/验证状态和一次提前强制 Finish 可执行，不能证明末端预留在真实模型中必然解决所有收尾失败。

v29 插件发生过最后一次请求验证通过、后续 Finish 超额；v30 没再出现此模式，但新轨迹更短且规则已改变，不能把差异作为严格因果修复证明。更不能将共同框架改动归为插件独有收益。

## 两个失败样本

- 插件 Click r2：SDK 状态 stuck，38 次读取、35 次相同范围重复，主要重复 core.py 的 1–60 行；没有修改代码或运行公开测试。首次宿主验收失败后反馈纠错仍陷入重复，19 次 Agent 请求后停止。
- 无压缩 Click r3：SDK 状态 stuck，28 次读取、23 次相同范围重复，末段重复 core.py 的第 1 行；没有修改代码或运行公开测试。25 次 Agent 请求后停止，宿主反馈纠错未解决。

两者最终均 16 failed、112 passed，未实现功能；不是文案大小写的单项误差，也不是预算耗尽。之前运行中的“模型提前结束”描述经原始事件核对已更正为 SDK 重复动作检测停止。新的验证门槛正确阻止将 SDK 停止计为任务成功。

相同范围计数是轨迹诊断，不能断言所有重复读取都无用；失败末段无编辑且重复目标范围，有明确停滞证据。无压缩也出现该问题，现有两样本不足以断言压缩导致停滞。

## 下一步与结项表述

优先处理大文件定位及重复读取：提供有边界的本地符号查找、记录已读位置与文件版本、在相同版本连续重复且无进展时引导定位新区域。需另存版本，先用这两条失败轨迹做零 API 测试，不关闭 SDK 停滞检测、不重跑覆盖 v30 失败。通用工具或完成策略对三组统一，插件专属改变另做消融。

保留 v11 为候选。本轮有输入减少证据，但插件未达到 6/6 正常完成门槛，原生摘要在完成率上更好。37.35% 与旧 15.18% / v29 13.91% 属不同协议和随机轨迹，不能写成算法单调优化曲线。结项可列本轮全部结果，同时写明已见任务、两个失败、未触发压缩样本、预算边界真实覆盖不足和同人任务设计限制；补充独立效果需新任务。
