## 1. 封存代码与证据（约半天）

1. 检查本模块 Git diff，按文件范围提交；README 依照现有仓库规则保持不提交。
2. 保存正式 manifest、依赖锁、原始 report/ledger、SDK 事件、最终工作区、测试日志、插件状态及 audit。
3. 单独保存 smoke 与预实验故障账本，注明开发调用不包含在正式效果统计中；SDK 价格缺失，费用只能以供应商账单核对。
4. 每项结项表格写明来源报告、分母、指标定义、模型与版本；不用不同任务集的节省率混算一个总收益。

验收：另一人在新输出目录按协议可运行；原始结果与审计结论可追溯。

## 2. 解释失败与收益波动（约一天，先做离线分析）

1. 逐项比较空值注释任务的模型轨迹：基线有两次触及调用上限，原生摘要有两次最终测试不通过，插件有一次修复正确后触及调用上限。
2. 查看插件的九对逐对输入收益；尤其标记多读文件、重复编辑、最终检查增加调用，以及未触发压缩的短任务。
3. 区分“压缩一次后的视图缩小”与“整项任务输入变少”；后者包括 Agent 行为变化，所以不能由单次压缩率直接推出。
4. 将这些病例写入结果讨论，不删除负收益点，不重跑失败直到成功再替代旧数据。

验收：能解释为何插件中位数为 14.80%，平均却只有 0.87%；答辩时主动说明未达到 30% 伸展目标。

## 3. 判断是否需要补实验（需要时约 3～7 天）

当前已有自然源码任务层证据，下一步补实验应验证新的假设。若时间允许，选择不同公开项目及 15～50 轮任务，先以少量 pilot 选择可实现的预算，再冻结任务、测试、重复数与参数。保持三组同模型、同工具、同权限，并计入摘要成本、失败样本、峰值、延迟、重复工具行为和关键约束。

若需要声称 OpenHands 上的完整生命周期创新，则先添加归档恢复工具、真实错误/模型/工具事件钩子与故障恢复评分，再独立冻结恢复或消融协议。目前的三组结果不能代替该验证。已有阶段二消融与其他宿主恢复证据可独立引用，不能当成 OpenHands 已实现的功能。

若结项期限很近，可直接以现有证据完成材料，把长任务和自动恢复写入限制与后续计划。

## 4. 整理论文或技术报告（约 2～3 天）

建议章节：问题与目标 → 相关工作 → 生命周期模型 → 模块实现与可插拔接口 → 实验协议 → 结果与失败案例 → 限制 → 总结。

结果分开呈现：阶段二冻结实验、LangGraph、真实文件工作区、跨类别接入、Dify 合成宿主验证、本次 OpenHands 公开源码任务。每层明确证明什么、尚不能证明什么。三项创新分别对应已有消融证据或待补证据，保留来源与恢复机制的具体示例。

验收：每个量化结论有证据路径；结果和限制一致；参考文献来自官方文档与原论文；没有“适配所有 Agent”或“普遍节省 30%”等越界结论。

## 5. 准备演示（约一天）

准备一个可复现的成功任务、一份带源事件 ID 的压缩轨迹、一例失败或负收益。演示顺序：任务 → 原始工具结果 → 模型视图压缩 → 文件修复与测试 → 三组汇总。预先保存结果用于断网或模型故障时展示。

验收：5～8 分钟能说明任务、创新、实际收益和限制；API 密钥与本机私有路径不出现在公开截图里。
