## 语言版叙述

**一句话结论。** 在该主机配置下，这款上下文插件在 3 个未触碰的封存任务上、5 重复、共 45 个样本中，把配对的**完整供应商 token** 降低了 **12.54%**（13/15 配对为正，自助法区间 [+5.17%, +18.30%] 不含 0），同时**三臂 45/45 全部通过严格轨**、插件零渲染失败；但它是靠**去除冗余**做到的——在没有任何冗余的读形状上，实测节省是 **0.00%**。

**为什么这个结论站得住。** 任务在**任何付费请求之前**完成来源登记与视图规则冻结（视图规则先于探针、一次诚实修订且旧文本与哈希保留），矩阵、上限（520，最坏情形 1.33×）、判定线与停止条件全部**前瞻预注册**；判据写在**全体配对**上，报告项（轨迹匹配子集、逐臂调用分布）**明确不得替代主判据**；批次目录一次写定、拒绝覆盖；随后由**独立审计**自算冻结合同与模块哈希、按记录逐行重算四条件与账本，得出 `complete=true/errors=[]`、`usable_as_saving=true`。历史批次（v12–v15、三次获取、两个开发小试）**一律未重判**。解封引用旗标也不是改冻结文件，而是**由新产物执行冻结自己预注册的解除条件**。

**数字与质量。** 池化 +12.54%，逐任务 +23.42% / +13.30% / +0.90%，峰值输入节省 27.27%，离散 σ 13.75pp。质量侧没有任何妥协的痕迹：三臂四条件 45/45，插件零渲染失败、零超长、零截断、零字段丢失，重试后仍失败为零。同批对照里，**原生摘要按同一口径是 −13.25%（净亏）**——它的摘要是额外 token，不是冗余。

**④ 为什么只给"带条件"。** 主判据本身是通过的（三条子条件全中），但 15 个配对里有 **2 个为负（−19.4%）**，成因已精确定位：插件臂**单方面**多花了一次**计费的修复重试**（输入 3,262 token），超过了那个任务的全部节省（≈1,416 token）；同一任务**没有重试**的三个重复则是 +14.4%。也就是说：**节省在轨迹与重试负担对称时稳定存在（13.2%–23.4%，σ ≤ 0.5pp），但会被单向重试吃掉**。轨迹匹配子集（n=13，+17.45%、σ 4.93pp）只能作解释，**永远不能替代主判据**。

**机制是什么。** 这条线上真正在跑的是**冻结的 v12 精确重复规则**，装在插件臂、且前面还有一道**预算触发门**。当协议要求每个视图读两遍时，基线臂约一半的读载荷是"仍然在上下文里的逐字重复"，插件去掉的就是这部分。三道屏障逐一验证：门（何时运行）、方法遮蔽（运行哪条规则：`_filter`/`_output_decision` 属 v8，其判据状态唯一写入者恰是被遮蔽的 v7 方法 ⇒ 无从删起）、以及**决定性的字面守卫**——它拒绝删掉任何"独家承载已登记必需字面"的内容（实测 `3.8.3` 在整个载荷里只存在于那一个输出）。**守卫拒得对**：删了就破坏严格轨。因此插件的能力边界可以被一句话说清：**只去冗余、绝不丢独家证据**。

**由此划定的范围。** 可以写"在该主机配置下、这 3 个任务、5 重复、按完整 token 计，配对节省 12.54%，且无冗余形状实测 0.00%"；**不可以**写"插件能压缩约 12.5% 的上下文""四判据达成""压缩单独省了 X%""节省随轨迹长度增长"，也**不可以**拿它主张跨宿主或跨配置的普遍有效。同理，**不得**靠"让协议多读几遍同一视图"去抬高数字——那是制造效应而不是测量效应。

**顺带得到的两个可迁移结果。** 其一，**重试税的根因是首答提示缺一条被强制的规则**（32/32 次重试都是"声明字面未落在渲染行内"，而提示从未说过必须落在 cause/fix 里）：补上那一句后，开发小试的首答接受率从 **28.9% 升到 77.8%**、每样本重试从 **0.711 降到 0.222**，严格轨 9/9 不变；且拒收类随即迁移为长度类（2/9），说明**上限现在是首答的第一瓶颈**。其二，**凡"跑完才执行"的管线都必须在零 API 门禁里被真跑一遍**——finalise 路径连续三次（v17、v19 两批、v20 门）是这条线上最贵的教训，而 v20 门禁正是靠这条断言在**花一分钱之前**拦住了付费。

**成本。** 整条 Agents 线累计约 **579 请求 ≈ $0.04**（全程非高峰），其中可引用的封存确认批本身约 $0.015–0.017。

**还能往哪走（诚实回答）。** 靠**测量**已经没有提升空间了：能测的形状、能接的机制都测过了。要更大的数字只有两条路，且都不是"再花几毛钱"能解决的——**(一) 设计新机制**：在保证据的前提下压缩"非冗余内容"（现有机制的守卫会在证据载体唯一时一律拒绝，这是设计使然）；**(二) 换登记**：构造"必需字面有多个载体"的任务，使守卫允许删掉其中一个载体（这需要新的来源登记与前瞻冻结，属于新一轮工作量）。
