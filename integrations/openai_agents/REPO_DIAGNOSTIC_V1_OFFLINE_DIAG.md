# OpenAI Agents 公开源码诊断开发批：失败轨迹离线审查

审查对象：`runs/stage5-openai-agents-api/openai-repo-diagnostic-v1-dev-01/` 的 `samples.jsonl`、`audit.json` 和当前冻结运行器/适配器源码。只读分析，无模型 API 请求；没有改动冻结运行器、审计或原结果。审计原结果为 27/27、104 次请求、`complete: true`。本报告专看 `pylint_regex_csv` repeat 2 与 `django_count_annotations` repeat 0–2。

## 保存了什么，缺了什么

该批目录只有 `manifest.json`、`samples.jsonl`、`report.json`、两份 CSV、`audit.json` 与 `RESULTS.md`，**没有逐调用模型输入或压缩前后视图文件**。运行器的 `RecordingRetryModel.inputs` 在进程内记录了过滤后的输入，但 `run_case()` 仅把工具名、用量、压缩计数、结构指标和最终输出写入样本行（`run_openai_agents_api_experiment.py:109,146,356–446`）。因此本轮不能逐字证明某条修复约束出现在失败样本的最后一次模型输入，也不能证明它被删除了。

适配器 `openai_agents.py:225–304` 把 Responses 非普通消息片段作为保护组，压缩后按 ID 原样恢复；恢复失败时会回退原输入。所有相关插件样本的 `structure_safe=true`、`restore_failure_count=0`、`unmatched_call_count=0`，且有保护组计数。这支持**工具调用/返回结构未损坏**；若源码工具返回位于这些保护组内，适配器代码保证其组内容原样恢复。但样本未存保护组清单或实际最终输入，不能由计数单独核实每段源码在模型端的存在性。普通用户问题陈述与任务约束可能在可压缩消息中，需输入快照才能判断实际保留情况。

## pylint repeat 2：压缩后答错，但首次轨迹已分叉

| 臂 | 输入 token/调用 | 压缩/摘要应用 | 最终规则 | 冻结质量 |
|---|---|---:|---|---:|
| none | 1679, 1861, 3018, 3714 | 0 | 仅在正则量词花括号外拆逗号 | 通过 |
| pruner_v1 | 1679, 1857, 1869, 2565 | 2 次压缩 | “逗号后有空白或结尾才拆” | 失败 |
| native_summary | 1679, 1857, 3014, 3710 | 摘要请求 2 次、应用 0 次，`summary_not_smaller` | “括号/方括号/花括号外才拆” | 失败（缺冻结必需词 `quantifier`） |

三臂都调用了 `read_pylint_option → read_pylint_transformer → read_pylint_csv_helper`，无工具/结构错误。插件后两次输入显著变短，说明压缩确实改变了上下文。**但插件和原生摘要臂的第一次模型输出各为 32 token，基线为 36；三臂第一次模型输入同为 1679 token，尚无输入大小不同的证据。**轨迹很早就发生分叉，且原生摘要臂没有应用摘要仍给出不同规则。原生摘要的失败由冻结答案门控缺 `quantifier` 一词触发；“括号外拆”是否能满足所有合法正则，需要另行构造反例，不能仅据本批称为实际语义错误。插件的“空白或结尾才拆”则确实无法覆盖无空白的多正则列表。故“压缩造成了 repeat 2 的错误”目前只是可能原因，不能从本批证明；模型采样/服务端非确定性或早期输出差异也可能影响后续。repeat 0/1 插件使用同类工具和两次压缩仍通过，进一步限制了单因解释。

## Django repeat 0–2：稳定质量退化，但缺因果快照

| 臂 | 成功 | 模型输入 token/调用 | 应用压缩 | 最终要点 |
|---|---:|---|---:|---|
| none | 3/3 | 每次 662, 2212 | 0 | 删除未被过滤、其它注解或排序引用的注解 |
| pruner_v1 | 0/3 | 每次 662, 2077 | 每次 1 | `preserve_annotation_select_mask_when_pruning`，未给引用判定 |
| native_summary | 2/3 | repeat 1/2 为 662, 2212；repeat 0 走 4 次调用 | 应用 0 | repeat 1/2 正确；repeat 0 语义正确但 223 字符，超 160 字符合同 |

插件三个重复的工具名、用量序列和错误输出均相同：先调用三个源码工具，第二次模型调用前各触发一次压缩，最终只说保留 annotation select mask。基线三次均正确。第二次模型输入由 2212 降到 2077 provider token（少 135），且插件保护组计数为 1、结构与工具门控均通过。**压缩与质量下降在这个固定轨迹中稳定同现**，值得优先修，但缺少真实压缩视图，不能断言删除的是问题陈述中“过滤/其它注解/排序”的引用条件，也不能排除压缩改变措辞后模型自行选错关注点。原生摘要三次都报告 `summary_not_smaller`，实际未应用摘要；其中 repeat 0 的失败只是冻结的长度约束失败，不能算语义失败。

## 可执行的后续验证

1. 在**新批次**运行器中保存每次过滤前后模型输入的本地快照或最小证据字段：每个工具返回的 SHA256、关键引用约束是否逐字出现在最终输入、保护组 ID/成员哈希、压缩前后消息数和输入哈希。快照只含这些公开 issue/基线源码，密钥字段始终不序列化。把采集逻辑及独立审计先冻结，再付费运行；不能从旧结果补造实际输入。
2. 为 Django 前瞻性检验“引用条件保留”策略，并在新批次沿用原质量合同；同时核对插件是否只是从问题陈述删掉了条件，而源码工具片段仍在。pylint 需同前缀或重复更多次，分开比较压缩前已分叉与压缩后才分叉的样本。
3. 报告质量与成本时保留全部失败样本。当前插件 2/9 对基线 6/9 的质量劣势使 +9.04% 完整 token 描述值**不构成有效节省**。
