# CrewAI r11 工具序列批：修「压缩打断工具调用序列」（同任务集，机制唯一变量）

本协议冻结在付费运行**之前**。冻结文件 `integrations/crewai/PRE_RUN_FREEZE_TWO_ROLE_R11_TOOLSEQ_MULTITASK_01.json`（付费）与 `..._MOCK_01.json`（零 API 栅格）。

## 1. 本批只修一处：压缩后工具调用/观测对必须完整且在序

r10（`runs/stage5-crewai/crewai-two-role-r10-fresh-multitask-01`）已证明 v9 钉住机制可迁移：首轮事实齐全 16/16、补救 0、全前缀回退 0。但同一批插件臂质量从基线 16/16 掉到 6/16，记录到的成因是**呈现**问题而不是事实丢失：

| r10 失败类别 | 数量 | 记录证据 |
|---|---:|---|
| 第一角色工具序列被压断 | **6** | `window_gate` 4 个样本整条任务只调用了 `check_window_lock`（3 个工具里只调 1 个）；`credential_rotation` 重复 2/3 调用顺序不符 |
| 决策者回抄合同占位符/错决策 | **4** | `decision=<RETRY>`（3 次）、`decision=PROCEED`（1 次） |

r11 **只加两条确定性保证**，v9 的三层（逐字证据钉住、任务合同钉住、计数型全前缀回退）全部保留、逐字不变。

## 2. 机制：v11 = v9 + 两条 host 指令（`crewai_tool_sequence_v11.py`）

`VerbatimToolSequenceMiddleware` 继承冻结的 r9 中间件，重写 `before_model`，**只看冻结任务记录与压缩前的原始历史，绝不看模型行为**：

1. **保证 A：工具序列指令。** 从**原始**（压缩前）历史里按 host 自己的 ReAct 标记逐条统计已经发生的工具调用（`Action: <name>` 且同一条消息带 `Action Input:`）；只要冻结工具表里还有未被观测到的工具，就追加**一条**指令消息，逐字给出冻结工具名及其冻结顺序、已调用清单、以及**下一个必须调用的工具**。该指令一直存在到全部冻结工具都被观测到为止，因此压缩视图无法让第一角色提前结束工具循环。效果**事后**由冻结工具表核对：插件臂工具序列必须与同重复基线一致。
2. **保证 B：决策合同指令。** 对决策角色，当投递视图已不再完整包含冻结 `RESULT` 合同句时，把该合同句**逐字**（含 `decision=<...>` 模板）追回，并附一句固定措辞的提示：模板中的尖括号是示例，必须写成冻结决策词与工具原值、**不得输出尖括号**。**模板故意保留可见**，因为「看不到模板」正是模型自动补全占位符的成因；隐藏它不在本批机制范围内。

两条指令都是 host 生成的普通 `{"role","content"}` 消息，不含任何冻结事实字面量，因此不会替模型满足 `handle_facts`；上限各 1 条（`MAX_TOOL_DIRECTIVE_MESSAGES` / `MAX_CONTRACT_DIRECTIVE_MESSAGES`），并逐样本计入 `tool_directive_events` / `contract_directive_events` 及其消息数。三条 v9 层与 tier-3 全前缀回退（含 `required_fact_whole_prefix_fallbacks` 与原因账本）**全部保留**。

**为什么不改动压缩本身**：r10 的证据显示工具调用/观测对本身由适配器的受保护组逐字恢复（`crewai_group_restore_failure_count` 全 0），真正缺席的是「还必须调哪个工具」这条指令。r11 因此只在**投递视图**上补回指令，不动压缩算法、不动受保护组、不动判据。

## 3. 一等门控指标（付费前冻结）

| 指标 | 定义 | r10 实测 |
|---|---|---|
| `tool_sequence_consistent` | 第一角色记录的工具有序列 = 冻结任务的工具表（同序、各一次） | 基线 16/16、插件 **10/16** |
| `tool_sequence_matches_baseline` | 插件臂某 (任务, 重复) 的第一角色工具序列 = **无压缩臂同键**的记录序列；整栅格跑完后统一计算 | r10 未记录该字段 |
| `first_pass_facts` | 冻结 r9/r10 定义：任何补救调用之前首轮 HANDOFF 含全部 `handle_facts` 字面量、单行 ≤450 字符 | 三臂各 16/16 |
| 严格 / 语义质量 | 冻结 r8 判据（v11 只路由任务路径，规则逐字不变） | 基线 16/16、插件 6/16 |
| 补救调用数 | 计入本臂与全局账本 | 0 |
| 完整总 token | agent 输入+输出+摘要输入+输出，含每次辅助请求与失败 | 135,487 / 119,667 / 169,777 |

**验收线（预注册）**：插件在 `tool_sequence_consistent`、严格质量、语义质量三项上**都不劣于**无压缩臂，且完整总 token 配对均值为正。任一不满足即判 `not_yet_valid`，并在审计中写明「本批数字不得当作有效节省」。审计还要求抽到 `errors` 非空时同样禁止作为有效节省引用。

## 4. 同任务集对照与矩阵

**任务集不变**：`tasks/stage5_autogen/natural_tasks_r10.json`（哈希 `873a306b…`，与 r10 冻结完全相同），因此 r10↔r11 的差值只在**机制**这一维度上。矩阵 4 任务 × 4 重复 × 3 臂 = **48 样本**；臂顺序按 r4 `balanced_plan` 轮换；重复间载荷完全一致；`deepseek-v4-flash`、温度 0、禁用 thinking；provider soft/target/hard = 1200/900/3000；`fixed_reserved_tokens=300`；输出 ≤512；摘要 ≤1024 token/角色 ≤4 次。

**全局请求上限 440**，算术：最少 agent 请求 = 2 × 48 = **96**；`native_summary` 臂病态最坏摘要请求 = 2 角色 × 4 次 × 48 = **384**；440 = 96 + 344（最坏值的约 90%），比 r10 同栅格实测 **319** 高约 34%。v11 的工具序列指令会把插件臂从 r10 的 88 次请求推回基线的 96 次（16 样本 × 6 次调用），预期总量约 **327**，上限保留 >25% 余量。若触顶则停止、保留部分目录、按新 id + `--resume` 续跑，不把部分栅格当完整栅格。
