# v46 Django 15563 三组开发小试冻结说明

v46 是 v45 的**环境与提示修正版**，任务、源提交、模型、端点、工具、导航、预算策略、阈值与各项上限**与 v45 完全一致**，仅修三处已证实的缺陷。v45 的原始结果与冻结文件保持不变，不得覆盖。

## 1. 与 v45 的差异（仅此三点）

1. **临时目录重定向**：实验进程及其所有子进程的 `TEMP`/`TMP`/`TMPDIR` 指向 `<输出目录>/.runtime-tmp`，在任何 SDK 导入之前设置。v45 中宿主沙箱拒绝写入机器 `%TEMP%`，导致 (a) SDK 文件编辑器历史缓存 `PermissionError`（插件两臂各 2 次、无压缩臂 0 次，属组间不对称干扰），(b) 宿主测试自身的临时目录清理失败，该错误还进入了模型可见的失败反馈。此改动不改变任何模型可见内容，不暴露参考修复或宿主测试。
2. **提示词不再诱导提前收手**：v45 首阶段提示含 “use finish immediately”，且未要求"必须先真正改动源码"。无压缩臂据此在 **9 次请求、零编辑** 的情况下提交，把配对分母压到 122,289 token，使组间输入比不可比。v46 要求：未实际编辑允许文件前不得 finish；改完须跑 `scoped_tests` 并读结果；**请求有剩余不是提前停止的理由**。
3. **纠错提示明确化**：纠错阶段要求必须落地真实编辑并重跑 `scoped_tests`，明确"不改变任何允许源文件的纠错不可能成功"。

v45 曾疑似"宿主反馈中文乱码"，经原始字节核对**不成立**（`evaluation-first/test.txt` 及 SDK 事件均为合法 UTF-8，字节 `25298,32477,35775,38382` 即"拒绝访问"），属控制台显示假象，故 v46 **未做编码改动**。

## 6. 本轮的解读前提

v46 相对 v45 同时改动了环境与提示，因此**两组结果不能互相归因到单一变量**。v46 的作用是检验"v45 的失败是否主要来自基线早停与沙箱干扰"；若基线恢复到 24 次请求量级，v46 才具备与插件臂比较的资格。

## 7. 零 API 验证中查明的边界（必须如实记录）

1. **"宿主反馈中文乱码"不成立。** v45 的 `evaluation-first/test.txt` 与 SDK 事件均为合法 UTF-8，字节 `25298,32477,35775,38382` 即"拒绝访问"。此前的乱码是读取端按 GBK 解码造成的显示假象。v46 未做编码改动。
2. **临时目录重定向已生效但未消除 `WinError 5`。** 该报错来自实验解释器退出时的 `atexit` → `shutil.rmtree`，清理的是 Django 测试自建的临时目录；测试结果在退出前已正常产出（v46 门控：`Ran 32 tests` → `FAILED (failures=2, expected failures=1)`，与冻结预期一致）。沙箱以受限 ACL 保护实验进程创建的目录，连宿主会话本身都无法遍历。**因此：在 DSH 沙箱内运行时，此退出期清理噪音只会改变路径（机器 `%TEMP%` → `<out>/.runtime-tmp`），不会消失；在普通终端运行时应消失。** 若把 v46 的输入差异当作插件效果，必须先确认批次的运行环境。
3. **v45 的编辑器 `PermissionError` 属沙箱目录保护**（写入沙箱管理的 `%TEMP%` 子目录被拒），不是模型编辑能力问题：该样本在错误后仍成功写入 `subqueries.py` 并以 30 次请求结束。v46 的重定向把它移到项目内目录，同时该报错确实出现在模型可见的宿主反馈中（v45 无压缩臂反馈里含 `1x PermissionError: [WinError 5] ... Temp\dsh-0Z2bzh\django_*`）。
4. **建议的运行环境**：付费批次由 DSH 沙箱内的工具调用启动，因此上述退出期噪音与目录 ACL 在本机路径下无法彻底消除。若要求与历史各轮（用户在自己终端运行）环境可比，付费批次应在普通 PowerShell 会话中执行。

### 结论与解读边界

1. **v45 的 −255.09% 已确认为基线早停伪影。** 修复提示后基线从 9 次→14 次、122,289→261,836 token，并首次真正编辑了源码；同一实例上 Pruner 的配对节省随之从 −255.09% 翻转为 +12.98%、峰值视图从 +3.7% 变为 **−19.0%**。
2. **但这不构成收益结论。** 三组质量全不通过，双方成功配对数为 0；Pruner 的节省与"编辑后代码仍然失败"来自不同轨迹，且相对的是失败的基线。按协议，主统计须包含失败样本，单任务单次只作开发信号。
3. **绝对输入并未普遍下降**：基线/原生摘要的绝对输入高于 v45（请求数增多），只有 Pruner 的绝对输入（227,840）低于 v45 的自身值（434,242）。因此不能说"压缩降低了总成本"，只能说"本次三组轨迹可比时 Pruner 的配对输入更低"。
4. **沙箱干扰在本轮更对称**：AgentErrorEvent 为 3／3／4（v45 为 0／2／2），不再单侧集中；两次编辑尝试的失败模式与错误分布仍未达到理想干净度。
5. **本地环境限制再次确认**：`TEMP/TMPDIR` 重定向到 `<out>/.runtime-tmp` 后，编辑器 `oh_editor_history_*.json` 写入仍被沙箱 ACL 拒绝（错误路径从机器 `%TEMP%` 变为项目内，未消失）。该缺陷无法在 DSH 沙箱内消除。
6. 按预注册停止规则，**不应把 v46 扩大为效果确认**；本实例（`django__django-15563`）已连续两轮在三组条件下均无法完成，应保留原始样本并按冻结顺序另选新实例。
