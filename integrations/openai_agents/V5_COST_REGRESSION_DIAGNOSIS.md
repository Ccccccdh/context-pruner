## 1. 被诊断的事实

| 臂 | 严格质量 | 实际输入 token 均值 | 完整总 token 均值 | 模型调用均值 |
|---|---:|---:|---:|---:|

配对完整总 token 均值 **−79.79 %**（正 0/3）。插件每次调用的输入 token 为 **662 / 2,075 / 2,476**，基线为 **662 / 2,212**（三次重复逐字一致）。

## 2. 分解结果：−79.79 % 主要由什么构成

单位是 provider input token（三次重复均值）。基线与插件逐边界对齐比较，`residual ≈ 9e-13`，即四项相加可精确重建插件总量：

| 项 | 数值 | 占输入回退的份额 |
|---|---:|---:|
| 基线输入总量 | 2,874 | — |
| **(a) 多走的一次模型调用** | **+2,335.8** | **+99.85 %** |
| (a2) 其中被假阳性回退挡掉的压缩 | +140.2 | +5.99 % |
| (b) 固定文本造成的载荷膨胀（同一边界比较） | **−136.7** | −5.84 % |
| 插件输入总量 | 5,213.3 | — |
| 输入回退合计 | +2,339.3 | 100 % |

三个结论：

1. **多走一次模型调用压倒性地主导（约占 99.9 %）**，而且这一次调用的成本（2,476 token）比基线与插件在共享两次调用上的全部差异（90 token）大一个数量级。
2. **"重传固定的 4,896 字符"在这一批里不是回退来源，反而略微有利。** 插件的第 2 次调用（2,075）比基线的第 2 次调用（2,212）**少 137 token**，因为 v5 仍然省掉了 `read_django_count_entry`（897 → 注释）。v5 的固定策略把承载约束的两个输出整份保留，但它在同一边界上仍然比基线便宜。
3. **被假阳性挡掉的压缩约 140 token**（占回退 6 %）。按同一比例换算，修好 v5 的组基线假阳性只能把插件输入从 5,213 降到约 5,073，完整总 token 仍约 **−71 %**，方向不变。
4. 因此 v5 RESULTS.md 第 4 节的三条原因排序需要修正：**"载荷膨胀"不是主导项**（它是负项），真正的主导项是**调用轮次**；"修好假阳性仍为负"这一判断本身是对的。

## 3. 是"固定"本身导致多走一轮吗

**不是。** 本批证据能支持的是三件事，脚本逐条列出：

1. **固定没有触发预算回退。** 插件送出的最大载荷是 **10,382 字节**，而冻结硬上限是 **65,216 字节**，余量 **6.28 倍**；整批 `budget_fallbacks = 0`，唯一的回退原因逐样本都是 `protected_tool_group_changed:baseline:responses-...`。
2. **那一次回退不是载荷变化引起的。** 每个插件样本第 3 次调用的 `filter_before` 与 `filter_after` 的 `input_bytes` 与受保护组哈希完全相同（`tests/test_openai_agents_group_baseline_diagnosis_v5.py` 已在零 API 下复现）。也就是说第 3 次调用**本来可以压缩**，是 `_group_hashes` 的基线假阳性让它没有压缩 —— 但那次调用**已经发生**，压缩与否不改变轮次。
3. **轮次与"是否省略了承载约束的大块输出"关系更紧。** 已记录批次的调用数：v3 插件 4（全量锚定后仍多走）、v4 插件 2/2/4（把 4,896 字符整份删掉，模型两轮收口）、v5 插件 3（保住承载输出、但省掉 `read_django_count_entry`）；三批基线都是 2。**本批证据无法证明某一次样本上模型的重新取回动作由哪段文本直接触发** —— 诊断不声称能证明因果，只报告可核对的相关性与边界数量。

**结论表述：多走一轮与"固定策略"没有可测的因果链；本轮次很可能由"载荷里出现的注释让模型重新调用工具"这一行为造成，而 v5 仍然保留了这样一个注释（非承载输出 `read_django_count_entry`）。** 对 v6 的含义很直接：**要么让被省去的输出不再是"模型需要回读的那一份"（在大输出内部按行范围省略、保留字面行与指针），要么接受轮次不变**。v6 选择前者。

## 4. v6 的零 API 投影

v6（`experiments/runners/openai_agents_span_retention_v6.py`）把"整份固定承载输出"换成**行范围省略**：注册字面所在行逐字保留，其余行区间被一个写明路径、省略行区间、保留行号与省略字符数的确定性指针替换，保留行与省略区间必须**恰好划分**注册范围。同一公开 Django 载荷序列在零 API 下驱动三个版本，估算载荷 token：

| 边界 | 基线 | v5（记录值一致性校验） | v6 |
|---|---:|---:|---:|
| 第 1 次调用（问题陈述） | 1,530 | 1,530 | 1,530 |
| 第 2 次调用 | 5,233 | 4,818 | **4,908** |
| 第 3 次调用 | 6,004 | 6,004 | **2,825** |
| v6 / v5 载荷比 | 1.00 / 1.14 / 1.00 | | **1.00 / 1.019 / 0.471** |

v6 在第三次调用上把载荷降到 v5 的 **47.1 %**（9,022 → 4,081 字节，节省 4,941 字节）。用同一边界的比值去缩放批次自己记录的每调用 token：

- **三轮轨迹（与 v5 同轮次，更保守）**：基线完整总 token 投影 **5,480**，v6 投影 **4,053**，配对节省 **约 +26.9 %**。
- **两轮轨迹（与基线同轮次）**：基线记录 2,962，v6 投影 **2,888**，配对节省 **约 +3.4 %**。这条是下界：基线作答的那次调用携带"最近一次工具组"，本机制任何版本都不省略它，v6 只能靠省略更早的输出来争取。

两条轨迹都为正，所以**付费小试的先验是有利的**；同时必须记住已记录的三批（v3/v4/v5）里插件臂都曾比基线多走调用，因此**两轮那条下界轨迹才是真正的风险点**，它的余量只有 3.4 %。投影不是 v6 付费批次的测量值，预注册验收线只适用于那个批次。
