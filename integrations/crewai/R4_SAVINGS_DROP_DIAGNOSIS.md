## 1. 结论（先回答"是否低于触发门"）

1. **三个任务的插件样本都越过了触发门，也都真的压缩了一次**：9/9 插件样本 `trigger_gate_triggered_calls ≥ 1`，9/9 有 1 次压缩事件。所以衰减**不是"低于触发门没触发"**造成的。
2. **衰减来自压缩量本身**，而不是门。9 个插件样本总节省空间只有 239/239/239（`release_readiness`）、239/239/239（`customer_migration`）、931/931/931（`incident_triage`，内部估算 token）。`release_readiness` 与 `customer_migration` 的上下文被压到 2314/2332 token，正是冻结的 `target_tokens=2314` 保留下限：17 条历史只删掉了 239 token（**9.3%**），而事故任务删掉 931 token（**36.6%**）。
3. **因此 `customer_migration` 的 +0.55% 配对均值不能称为"压缩收益"**：该任务插件三对的完整总 token 是 3931/3847/3879，无压缩是 3906/3906/3910，其中两对插件**更贵**；把它的实际 provider 输入差（−76.67 token/样本，即输入侧 +2.1% 反向）和输出差（+55 token/样本）加总后，成本差为**负**（插件更贵 21.67 token/样本）。该任务的 +0.55% 完全由输出 token 波动产生，不能归因于压缩。`release_readiness` 的 +3.99% 同理夸张：它的配对方向来自输出 token 差（插件比无压缩少 51.67 token/样本），输入侧的压缩收益只有 −109.33 token/样本，会被输出波动放大或抹掉。**只有 `incident_triage` 的 +11.85% 与压缩量级一致，可以作为压缩收益解读。**
4. 结构性原因：**一次任务里压缩只发生一次**（第一个角色的第 2 次调用），第二角色（决策者）从未触发（其估算载荷 1894–2045 token，远低于 3085 的软上限），且压缩后的视图不再越过门。收益 = 一次压缩省下的 token × 之后重发该历史的 3 次调用里的 2–3 次；保留下限越高，收益越小。

## 2. 触发门与压缩事件（逐任务）

软上限（估算 token）3085 = provider soft 1200 ÷ 标定比 0.389；`--fixed-reserved-tokens 300`。

| 任务 | 插件样本 | 越门样本 | 压缩事件 | 角色 1 越门/放行 | 角色 2 越门/放行 | 角色 2 峰值估算载荷 |
|---|---:|---:|---:|---:|---:|---:|
| `incident_triage` | 3 | 3 | 3 | 3 / 9 | 0 / 9 | 2008–2045 |
| `release_readiness` | 3 | 3 | 3 | 3 / 9 | 0 / 9 | 1894–1912 |
| `customer_migration` | 3 | 3 | 3 | 3 / 9 | 0 / 9 | 1962–1985 |

- 角色 1 每次样本压缩 1 次（4 次模型调用中的第 2 次之前），其余 3 次调用放行。
- 角色 2 的 2 次调用全部低于门，插件在该角色上**没有任何作用**；它的上下文只有 1990–3060 字符，即使不压缩也在门内。
- 9/9 插件样本没有触发缺事实补救（`recovery_invocations = 0`），补救调用数全批为 **0**；`native_summary` 的 6 次摘要请求（每样本 2 次）都计入本臂与全局账本。

## 6. 对 r5 的直接含义

1. 若要维持质量门槛下的稳定节省，必须选择**历史占比更高、保留下限以下仍有可压缩内容**的任务，或降低保留下限；仅靠"门会触发"不能带来节省。
2. 决策角色在 r4 从未进入压缩路径，因此 r4 的节省只来自第一个角色的历史重发；r5 任务设计应保证**两个角色都长期重发长历史**，否则跨任务收益仍会被保留下限压平。
3. 必须同时报告输入侧差与输出侧差，避免把输出波动读成压缩收益；`customer_migration` 就是反例。
4. 触发门与 `target_tokens` 的关系需在协议中显式写出（门 3085 估算 token、保留下限 2314），并预注册"压缩后仍然越门"的最少次数，否则收益无法外推。
