# CrewAI r24 覆盖守卫零 API 诊断

目标是修 r23 的质量失败，不追溯修改 r23。新机制见 `experiments/runners/crewai_coverage_guard_v24.py`；仍是开发阶段，尚无 r24 付费批或冻结。

## r23 六条失败的准确位置

四项任务的第一角色均应调用四个指定来源。r23 插件臂的 `ledger_lock_attestation` 与 `replica_resync_attestation` 各三次重复，均只在第一角色调用前三个来源就发出 `HANDOFF`。第四个来源后来由第二角色调用，因此跨角色合并的工具轨会掩盖第一角色漏读。该提前交接是宿主已执行工具数与角色边界的事实，不依赖输出文字声称已读过什么。

## r24 机制和离线证据

守卫在第一角色释放模型答复前，从宿主消息中带 `Observation:` 的实际 Action 计算已读来源集合。合同只要求每个来源至少一次，**允许任意顺序和重复**。覆盖未满时，无 Action 的 `HANDOFF` 被拒，附带仍缺哪些来源的宿主控制消息，再发真实模型请求；拒绝上限 6，触顶算失败。完整覆盖后放行。三臂须安装同一守卫，才能比较插件、无压缩与原生摘要。

`tests.test_crewai_coverage_guard_v24` 的 5 项零 API 测试通过：

1. r23 12 条插件首个交接逐条重放：六条漏读恰为 `reject_actionless`，六条完整恰为 `complete`；
2. 乱序、重复合法；文字自称完成不计作调用；未知工具历史拒绝；
3. 拒绝上限触发 `GuardExhausted`；
4. 模拟供应商的一次拒绝加一次重发准确消耗 2 个请求槽，并在第二次输入留下控制消息；
5. 原生摘要臂的新类也留下逐 Agent 尝试捕获，修复 r23 `native_summary` 臂捕获为空的缺口。

## 付费准入仍缺

尚未把新守卫接到真实 CrewAI 全臂 runner、摘要请求槽与新独立审计的完整网格。新审计必须硬性拒绝任一臂 `capture_complete=false`，并将“可引用”资格与质量、成本双门同时相连；需要针对 r23 的原生摘要空捕获和成本正但质量失败两条负控制。零 API 全链通过后，先用新 ID 小试，再用**新任务集**确认；r20/r23 任务已参与机制设计，不能当留出集。
